<objective>
Prove the entire Phase 2 architecture end-to-end on the thinnest possible path: a user with an unlocked vault fills in an API key entry, it is written into a new `entries` table inside the already-encrypted vault database, and it comes back in the vault's entry list.

This is a tracer, not a prototype. Every layer it touches is production code that later plans expand rather than replace: the unified `entries` schema (D-01), the Zod per-type payload contracts for all four entry types (D-02), the `requireUnlocked`-gated `entriesRouter`, the client API functions, and the entry list/form components.

Purpose: an architectural dead-end in the unified-table + JSON-payload model must surface after one commit, not after ten. Every subsequent plan in this phase builds on the seams this plan lands.
Output: a working create-and-list path for API key entries, an integration test that proves it round-trips through a real encrypted vault, and a schema-bootstrap seam that also upgrades vaults created in Phase 1.
</objective>

<assumption_delta_decision>
**Primary noun introduced:** `entry` — the vault's second core noun after Phase 1's vault key/session, and the first plural first-class noun in the data model.

**Decision:** `promote` — a single unified `entries` table holding all four types, with type-specific fields in an encrypted JSON `payload` column.

**Rationale:** user-directed in CONTEXT.md D-01/D-02. The add-alongside alternative (one table per entry type) is the anti-pattern here: cross-type search (ORG-03), tag filtering (ORG-02), and folder grouping (ORG-01) would each need a four-way UNION against four schemas that must be kept in lockstep. `folders`, `tags`, and `entry_tags` arrive in the same DDL pass as sibling nouns.

**Reversibility:** `costly` (carried from CONTEXT.md D-01). Splitting into per-type tables later requires a data migration across every existing entry plus a rewrite of every search/tag/folder query. Not `one-way` — the user already chose this door in `/gsd-discuss-phase`, so no decision checkpoint is inserted.
</assumption_delta_decision>

Wire ONE entry type (`api_key`) through every layer, from the React form to the encrypted SQLite file and back. No other entry type gets a UI, no folder/tag/search/trash code is written, no other call sites are added. Real error handling on this single path.

**Schema (`server/src/modules/db/schema.ts`)** — add four sibling table interfaces to `VaultDbSchema` alongside the existing `schema_version`, per D-01/D-02/D-06:
`entries` with columns `id: string`, `type: "api_key" | "login" | "note" | "card"`, `name: string`, `folder_id: string | null`, `payload: string`, `notes: string | null`, `created_at: string`, `updated_at: string`, `deleted_at: string | null`;
`folders` with `id: string`, `name: string`, `created_at: string`;
`tags` with `id: string`, `name: string`, `created_at: string`;
`entry_tags` with `entry_id: string`, `tag_id: string`.
Document in the file header that `payload` holds a JSON string of the type-specific fields and that it is protected by the whole-database-file cipher established in Phase 1 — there is deliberately no second encryption layer and no cleartext sibling column.

**DDL (`server/src/modules/db/connection.ts`)** — extend `initSchema` to create all four tables, preserving the existing `.ifNotExists()` convention and statement-at-a-time style already used for `schema_version`. Column types are all `"text"` except where noted; `id` columns are `col.primaryKey()`; `type`, `name`, `payload`, `created_at`, `updated_at` are `col.notNull()`; `folder_id`, `notes`, `deleted_at` are nullable. `folders.name` and `tags.name` get `col.notNull().unique()`. `entry_tags` gets a composite primary key over `entry_id` and `tag_id` via `addPrimaryKeyConstraint`. Add indexes with `createIndex(...).ifNotExists()`: `entries_deleted_at_idx` on `entries(deleted_at)`, `entries_folder_id_idx` on `entries(folder_id)`, `entry_tags_tag_id_idx` on `entry_tags(tag_id)`.
Make `initSchema` idempotent: the existing unconditional `insertInto("schema_version")` must only run when the table is empty — read the row count first and skip the insert when a version row already exists. This is required because `initSchema` becomes a per-open call in Task 2, and an unconditional insert would append a row on every unlock.

**Zod contracts (`server/src/modules/vault-entries/schemas.ts`, new)** — export `entryTypeSchema` as `z.enum(["api_key", "login", "note", "card"])`, and one payload schema per type per REQUIREMENTS.md's parenthetical field lists:
`apiKeyPayloadSchema` = `{ key: string min 1, endpoint?: string, model?: string }`;
`loginPayloadSchema` = `{ username: string min 1, password: string min 1, url?: string }`;
`notePayloadSchema` = `{ body: string }` (empty string allowed — a blank note is valid);
`cardPayloadSchema` = `{ number: string min 1, expiry: string min 1, cvv: string min 1, cardholder?: string }`.
Export `entryCreateSchema` as a `z.discriminatedUnion("type", [...])` with one branch per type. Every branch carries the same common fields: `type` literal, `name` (string, min 1, max 200), `folderId` (nullable optional string), `notes` (nullable optional string, max 10000 — this is D-03's freeform field, present on every type), `tags` (optional array of strings, each min 1 max 50), and `payload` (that type's payload schema). Export the inferred types `EntryType`, `EntryCreateInput`, and a `EntryPayload` union.
All four types are defined now even though only `api_key` has a UI in this plan — the discriminated union is one contract and splitting it across plans would force a rewrite of the union in 02-02.

**Service (`server/src/modules/vault-entries/entries.ts`, new)** — a module of functions over `getDb()` imported from `../auth/session.js`, following the `vaultMeta.ts` single-purpose-function shape. Export:
`createEntry(input: EntryCreateInput): Promise<Entry>` — generates `crypto.randomUUID()`, sets `created_at`/`updated_at` to one shared `new Date().toISOString()` value, `deleted_at` to null, serializes `input.payload` with `JSON.stringify` into the `payload` column, inserts, and returns the mapped DTO. It never dedupes or upserts: two calls with identical field values produce two rows with different ids.
`listEntries(): Promise<EntrySummary[]>` — selects only `id`, `type`, `name`, `folder_id`, `created_at`, `updated_at` from `entries` where `deleted_at is null`, ordered by `updated_at desc` then `id asc` so equal timestamps have a deterministic, stable order.
Export two mappers, `rowToSummary` and `rowToEntry`, converting snake_case columns to the camelCase DTO field names (`folderId`, `createdAt`, `updatedAt`, `deletedAt`). `rowToEntry` additionally `JSON.parse`s the payload column; `rowToSummary` must not read the payload or notes columns at all — the summary DTO has no such properties, and this is the mechanism enforcing the second prohibition in this plan's `must_haves`.
Export the `Entry` and `EntrySummary` interfaces from this module.

**Routes (`server/src/modules/vault-entries/routes.ts`, new)** — export `entriesRouter` from `Router()`. Immediately after construction, call `entriesRouter.use(requireUnlocked)` once at router level so no route in this module can ever be added without the gate — unlike `vaultRouter`, which has the one deliberate `/status` exception. Define exactly two routes in this plan: `GET /entries` returning `res.json(await listEntries())`, and `POST /entries` with `validate(entryCreateSchema)` returning `res.status(201).json(created)`. Both handlers use the `void (async () => { try { ... } catch (err) { next(err); } })()` wrapper. Do not construct `vaultAuthError()` anywhere in this file — that constructor is reserved for the unlock oracle; entry CRUD failures fall through to the generic 500 or are answered explicitly with a status plus an `{ error: string }` body.

**Mount (`server/src/app.ts`)** — import `entriesRouter` and add `app.use("/api/vault", entriesRouter)` after the existing `app.use("/api/vault", vaultRouter)` line and before `app.use(errorHandler)`. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser (`http://127.0.0.1:5173`) → Express API (`http://127.0.0.1:5174`) | Untrusted JSON request bodies cross here; any page open in the same browser can issue a simple request to the loopback API |
| Express API → keyed SQLite file (`vault.db`) | The only path across which entry data is written; the whole-file cipher from Phase 1 is the confidentiality boundary |
| in-memory session → disk | The Vault Key exists only in process memory; every entry write must go through the session-owned Kysely handle, never a second connection |
