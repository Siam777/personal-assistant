<objective>
Turn a flat pile of entries into a vault a user can navigate: flat user-defined folders, free-form tags created as they type, and a search box that finds an entry by name, folder, or tag.

Purpose: the phase goal is "store, organize, and **find**". Plans 02-01 and 02-02 delivered store. This plan delivers organize and find — the half of the goal that makes a vault with fifty entries usable rather than a list to scroll.
Output: a folder sidebar, a tag filter row, and a debounced search box that compose into one filtered entry query, plus the server-side folder, tag, and search machinery behind them.
</objective>

**`folders.ts` (new)** — a module of functions over `getDb()`, matching the `vaultMeta.ts` single-purpose-function shape. Export a `Folder` type of `{ id, name, createdAt, entryCount }` and:
`listFolders()` — selects all folders ordered by `name` ascending, left-joined against a count of live entries (`deleted_at is null`) per folder.
`createFolder(name)` — trims the name, rejects an empty result, inserts with `crypto.randomUUID()`. There is deliberately no parent-id parameter and no parent column: folders are flat per D-05.
`renameFolder(id, name)` — updates the name, returns null when the id is absent.
`deleteFolder(id)` — inside a single `db.transaction()`: first set `folder_id` to null on every entry whose `folder_id` matches, then delete the folder row. Entries inside a deleted folder become uncategorized, never deleted — this is the behaviour the UI-SPEC delete-folder confirmation promises the user.
Both `createFolder` and `renameFolder` surface a duplicate name from the unique constraint as a tagged error the route converts to 409 rather than a generic 500.

**`tags.ts` (new)** — export a `Tag` type of `{ id, name, entryCount }` and:
`listTags()` — every tag with its count of live entries, ordered by count descending then name ascending.
`setEntryTags(entryId, names)` — inside one `db.transaction()`: normalize each name by trimming and dropping empties and duplicates within the submitted list; for each remaining name look up the existing tag by name and insert one with a fresh UUID only when absent; then delete all `entry_tags` rows for this entry and insert exactly the rows for the resolved tag ids. Reusing an existing row by name is what keeps the `tags` table free of duplicates under D-07's create-on-the-fly rule. A tag row is never deleted here even when its last link goes away — it stays available for reuse.
`tagsForEntries(entryIds)` — one query returning a map from entry id to its tag names, so a list of N entries costs one extra query rather than N.

**`search.ts` (new)** — export an `EntryListFilter` type of `{ q?, folderId?, tag?, deleted? }` and two functions:
`escapeLikePattern(term)` — escapes backslash, percent, and underscore in the user's term so a query consisting of a bare wildcard character matches literally instead of returning the whole vault.
`applyEntryFilters(qb, filter)` — takes a Kysely query builder over `entries`, left-joined to `folders`, and adds: the `deleted_at is null` / `is not null` predicate from `filter.deleted`; an equality on `entries.folder_id` when `filter.folderId` is set; an `exists` subquery over `entry_tags` joined to `tags` on name when `filter.tag` is set; and, when `filter.q` is a non-empty string after trimming, an `or` group of case-insensitive `like` comparisons with an explicit escape character against `entries.name`, `folders.name`, and an `exists` subquery on `tags.name`. A blank or whitespace-only `q` adds no predicate at all, so the list comes back unfiltered rather than empty. This module must never reference the encrypted column that holds an entry's type-specific field values, in any select, where, order-by, or join clause — that boundary is non-negotiable regardless of search mechanism, and it is asserted by a source gate below.

**`schemas.ts`** — add `folderCreateSchema` (`{ name: string trimmed, min 1, max 100 }`), `folderRenameSchema` (same shape), and `entryListQuerySchema` validating the `GET /entries` query string: `q` optional string max 200, `folderId` optional string, `tag` optional string, `deleted` optional literal `"true"`.

**`entries.ts`** — three changes:
Change `listEntries(filter: EntryListFilter)` to build its query through `applyEntryFilters`, to select `folders.name` as the entry's folder name, to attach tag names via one `tagsForEntries` call, and to order by `updated_at desc, id asc` so equal timestamps have a deterministic, stable order across repeated identical requests. Add `folderName: string | null` and `tags: string[]` to `EntrySummary`; it still carries no payload and no notes property.
Change `createEntry` to call `setEntryTags(id, input.tags ?? [])` after the insert, closing the gap where the `tags` field has been part of the request contract since 02-01 without being persisted.
Change `updateEntry` to call `setEntryTags(id, input.tags ?? [])` after the update, so saving an entry replaces its tag links exactly.
Also attach `tags` to the single-entry `Entry` DTO returned by `getEntry`.

**`routes.ts`** — add to `entriesRouter`, all inheriting the router-level gate and the async-error wrapper:
`GET /folders` → 200 with the folder list. `POST /folders` with `validate(folderCreateSchema)` → 201, or 409 `{ error: "A folder with that name already exists" }`. `PATCH /folders/:id` with `validate(folderRenameSchema)` → 200, 404, or 409. `DELETE /folders/:id` → 204 or 404. `GET /tags` → 200 with the tag list.
Change `GET /entries` to parse `req.query` through `entryListQuerySchema` and pass the resulting filter into `listEntries`. Because `validate()` parses `req.body`, parse the query object explicitly inside the handler with `safeParse` and answer 400 `{ error: "Invalid request" }` on failure rather than adding a second middleware.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `GET /api/vault/entries?q=…` | An attacker-influenced search term crosses here and is used to build a SQL predicate |
| search predicate → the `entries` table | The query plan chooses which columns are read; this is the boundary that must never reach the encrypted field-values column |
| browser → folder and tag collection responses | Folder and tag names are user-authored strings rendered back into the DOM |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-14 | Information Disclosure | `search.ts` filter composition | high | mitigate | `applyEntryFilters` reaches only `entries.name`, `folders.name`, and `tags.name`; a source gate asserts the module contains no reference to the encrypted field-values column, so no query plan, timing signal, or result can leak plaintext from it. |
| T-02-15 | Information Disclosure | entry, folder, and tag collection responses | high | mitigate | `rowToSummary` still selects no payload and no notes column; test 14 in `organization.test.ts` asserts no element of any of the three collection responses carries a payload property. |
| T-02-16 | Tampering | user search term interpreted as a SQL wildcard | medium | mitigate | `escapeLikePattern` escapes backslash, percent, and underscore and every `like` comparison passes an explicit escape character, so a bare wildcard matches literally. Values themselves are bound by Kysely as parameters, never concatenated. |
| T-02-17 | Elevation of Privilege | new folder, tag, and search routes | high | mitigate | All are defined on `entriesRouter`, which applied `requireUnlocked` at router level in 02-01, so none can be reached with a locked vault. |
| T-02-18 | Tampering | `deleteFolder` destroying entries | medium | mitigate | Runs in one `db.transaction()` that nulls `entries.folder_id` before removing the folder row; a source gate asserts the transaction shape. The confirmation copy states the same guarantee to the user. |
| T-02-19 | Information Disclosure | folder and tag names rendered into the DOM | medium | mitigate | Rendered as React children, never via `dangerouslySetInnerHTML`; the search-match highlighter splits the string into text nodes rather than injecting markup, asserted by a source gate. |
| T-02-20 | Denial of Service | unbounded search term or tag count | low | accept | `entryListQuerySchema` caps `q` at 200 characters and the vault is single-user and local; a per-request cost ceiling beyond that is not warranted. |
| T-02-SC | Tampering | npm/registry installs | high | mitigate | This plan installs no package and adds no shadcn component; every primitive it uses was added in an earlier plan. |
