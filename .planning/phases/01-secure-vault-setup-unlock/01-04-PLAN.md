<objective>
Expand the tracer outward along the second-factor axis: a user with an unlocked vault can turn on
TOTP 2FA, save a set of one-time backup codes, and from then on must supply both the master password
and a valid code to unlock.

This plan adds no new architectural layer and no new unlock endpoint. Plan 01-03 already defined the
optional `totpCode` field on the unlock request and already renders the second-factor input from the
status flag, so this plan fills in the branch rather than reshaping the contract.

Purpose: 2FA is where a vault most often gets weaker rather than stronger — a second factor stored
as a plaintext convenience field, or a code that unlocks on its own, or a backup-code path that
skips the master password entirely. Each of those turns the second factor into the weakest link.
This plan makes each one mechanically impossible.

Output: an optional, confirmed-before-committed second factor whose secret is encrypted at the same
standard as vault secrets, with single-use backup codes and re-authentication gating on disable.
</objective>

    Build the server side of the optional second factor. Reuse the existing crypto, session, and

    **`totp.ts`** exports five functions.

    `beginEnrollment()` requires an unlocked session. It calls otplib's `generateSecret()`, builds
    an `otpauth://` URI with `generateURI({ issuer: "PersonalAssistant", label: <vault label>,
    secret })`, renders that URI to a data URL with `QRCode.toDataURL()`, and stores the pending
    secret in a module-private map keyed by a random enrollment id with a short expiry (a few
    minutes). The pending secret is deliberately not written to the sidecar yet — a user who scans a
    QR code and then closes the tab must not end up with 2FA half-enabled and no working
    authenticator. Return the enrollment id, the QR data URL, and the secret in its base32 text form
    for manual entry. This is the one place the secret leaves the server in plaintext, and it goes
    only to the same local user who is already holding an unlocked vault.

    `confirmEnrollment(enrollmentId, code)` requires an unlocked session. It looks up the pending
    secret, verifies the code with otplib's `verify({ secret, token, epochTolerance })`, and checks
    the `.valid` field on the returned result object explicitly. Testing the returned object for
    truthiness instead accepts every code including wrong ones, because a result object is always
    truthy. On success it: encrypts the secret with `wrapKey` using the **Vault Key** (not the
    Master Key — the Vault Key is what every other vault secret is encrypted with, and D-06 requires
    the same standard), generates the backup codes, writes `totp.enabled = true`, the wrapped
    secret, and the code hashes into the sidecar atomically, deletes the pending entry, and returns
    the plaintext backup codes. Those plaintext codes are returned in this one response and are
    never persisted and never re-servable.

    `generateBackupCodes()` produces ten codes, each from `randomBytes` rendered as a readable
    alphanumeric string in a fixed grouped format, and returns both the plaintext codes and their
    SHA-256 hex digests. A fast hash is correct here rather than Argon2 because the codes are
    already high-entropy and single-use; the hashing exists as defense in depth against the sidecar
    being read out of context, not as a brute-force barrier.

    `verifySecondFactor(code, vaultKey, meta)` is what the unlock handler calls. It unwraps the
    stored secret with the Vault Key and checks the supplied code with otplib, again reading the
    `.valid` field explicitly. If that fails, it hashes the supplied code and compares against
    `backupCodeHashes` using a length-safe constant-time comparison; on a match it removes that
    single hash from the array, writes the sidecar atomically, and reports success. A consumed code
    must be gone before the response is sent, so a replay of the same code within the same second
    cannot succeed twice. It returns a plain boolean and never explains which path matched.

    `disableTotp()` clears `totp.enabled`, sets `wrappedSecret` to null, and empties
    `backupCodeHashes`, writing the sidecar atomically.

    **`routes.ts`** gains four routes under `/api/vault/2fa`, all requiring an unlocked session:

    `POST /2fa/enroll` calls `beginEnrollment` and returns the id, QR data URL, and base32 secret.
    `POST /2fa/confirm` is validated by `{ enrollmentId: string, code: string }` and calls
    `confirmEnrollment`, returning `{ backupCodes: string[] }` on success and the generic 401 on a
    bad code.
    `POST /2fa/disable` is validated by `{ masterPassword: string }`. It re-derives the Master Key
    from the submitted password and the stored salt and re-unwraps the stored Vault Key to prove the
    password, then calls `disableTotp`. An already-unlocked session is deliberately not sufficient
    (D-06): the threat here is someone reaching a machine left unlocked, and re-authentication is
    what stops them turning the second factor off. Failures return the generic 401.
    `POST /2fa/backup-codes/regenerate` is validated by `{ masterPassword: string }`, performs the
    same re-authentication, generates a fresh set, replaces the hashes, and returns the new
    plaintext codes once — invalidating every previous code.

    Note that initial enrollment requires only an unlocked session, while disable and regenerate
    require the password. This follows D-06's wording, which names view, reset, and disable as the
    re-authentication cases. If you disagree with that reading, raise it rather than changing it
    silently — it is the one place this phase interprets D-06 rather than quoting it.

    Also complete the unlock handler's second-factor branch from Plan 01-03: when the sidecar reports
    `totp.enabled`, call `verifySecondFactor` after the Vault Key has been recovered, and convert a
    false result into `vaultAuthError()`. The ordering is load-bearing and must not be inverted: the
    master password is verified first by the auth-tag check, and the second factor is checked only
    after that succeeds. A code alone can therefore never unlock anything, because without the
    correct password there is no Vault Key with which to decrypt the secret the code is checked
    against. That property is structural rather than enforced by a conditional, and it is what makes
    this plan's `must_haves.prohibitions` entry true by construction.

    **`totp.test.ts`** — assert: a code generated by otplib for a known secret verifies, and a code
    from a different secret does not; the verification path reads the result object's `.valid` field
    rather than the object itself, proven by a test that feeds a deliberately wrong code and
    requires rejection; `generateBackupCodes` returns ten distinct codes whose digests match the
    returned hashes; `verifySecondFactor` accepts a backup code once and rejects the same code the
    second time; the sidecar after a backup-code consumption has one fewer hash; and a confirmed
    enrollment writes a `wrappedSecret` whose ciphertext, when the sidecar bytes are scanned, does
    not contain the base32 secret in either its text form or base64 form.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → local API (`127.0.0.1:5174`) | The master password and the second-factor code cross here together in one request. |

## STRIDE Threat Register

ASVS Level 1. Blocking threshold: `high`.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Elevation of Privilege | Second factor substituting for the master password | critical | mitigate | Structural, not conditional: the stored secret is encrypted with the Vault Key, which only the correct master password can recover, so a code cannot be checked at all without the password already having been proven. `two-factor-unlock.test.ts` assertion 4 proves it. |
| T-04-02 | Tampering | TOTP secret stored plaintext "because the vault is already encrypted" | high | mitigate | The secret is wrapped with the Vault Key using the same AES-256-GCM helper as every other secret (D-06); a sidecar byte scan in both `totp.test.ts` and `two-factor-unlock.test.ts` asserts the base32 form is absent in any encoding. Note the sidecar is the *unencrypted* file, so plaintext storage here would expose the secret outright. |
| T-04-03 | Information Disclosure | Unlock response revealing which factor failed, or that a second factor exists | high | mitigate | All 2FA failures route through `vaultAuthError()`; assertion 5 requires the missing-code, wrong-code, and wrong-password responses to be byte-identical to each other and to the single-factor wrong-password response. The client renders the server message unchanged, enforced by a grep. |
| T-04-04 | Elevation of Privilege | Backup code replayed after use | high | mitigate | `verifySecondFactor` removes the matched digest and writes the sidecar atomically before the response is sent; assertion 7 proves the same code fails on immediate reuse. Digest comparison is length-safe and constant-time. |
| T-04-05 | Elevation of Privilege | 2FA disabled by someone reaching an unlocked machine | high | mitigate | Disable and regenerate both require re-deriving the Master Key from a freshly submitted password and re-unwrapping the Vault Key (D-06). An unlocked session alone is deliberately insufficient, which is precisely the walked-away-from-machine case. |
| T-04-06 | Information Disclosure | Backup codes persisted or re-servable after enrollment | high | mitigate | Only SHA-256 digests are stored; the plaintext set exists in exactly one response body and in component state until acknowledged. No endpoint returns them again; regeneration replaces the whole set and invalidates every prior code. |
| T-04-07 | Spoofing | Replay of a TOTP code within its tolerance window | medium | accept | Accepted with rationale: RFC 6238 codes are inherently replayable inside their window, and single-use tracking would require persisting used codes to the sidecar on every unlock — extra writes to the vault's most fragile file for a threat that requires an attacker who already has the master password. `epochTolerance` is kept tight to narrow the window. |
| T-04-08 | Tampering | Half-enabled 2FA from an abandoned enrollment | medium | mitigate | The pending secret lives in an in-memory map with a short expiry and is never written to the sidecar until a valid code confirms it. A user who scans and closes the tab has changed nothing. On a primary trust boundary (the unlock path), so mitigated rather than accepted at L1. |
| T-04-09 | Denial of Service | User loses the authenticator device and all backup codes | medium | accept | Accepted with rationale: this is the direct consequence of D-05's no-recovery policy, chosen deliberately. The mitigation available is the one already taken — ten backup codes, shown with an explicit acknowledgement that they cannot be retrieved later. |
| T-04-10 | Information Disclosure | QR data URL or base32 secret reaching a log | high | mitigate | Both flow through the redacting logger from Plan 01-01, whose secret-name pattern covers a field named for a secret and whose Buffer rule covers the rendered image; no module writes to standard output directly, enforced by the repo-wide grep established in Plan 01-01. |
