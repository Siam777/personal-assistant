## Gap Closure — G-01-31

**Failed truth (UAT test 31, coverage_id D6 of Plan 01-01):** "Running `npm run dev` from an actual
interactive terminal and pressing Ctrl-C once cleanly stops all three child processes (tsc,
node --watch, vite) with no orphaned process left behind."

**What the user saw:** a `Terminate batch job (Y/N)?` question appeared, the `y` keystroke was not
consumed by it (PowerShell then tried to run `y` as a command), and two node.exe processes survived.

**Root cause** (from `.planning/debug/npm-dev-ctrlc-orphan-processes.md`, diagnosed 2026-08-19):
Windows delivers Ctrl-C as a console-wide broadcast to every process attached to the same console
at once. `scripts/dev.mjs` puts several Windows script shims (batch files) inside its own subtree
and leaves all of its children attached to that shared console, so the broadcast tears the tree
apart from the middle out — while dev.mjs's own `taskkill` calls are fired without ever being
awaited, and the compiled-server watcher's inner worker process is never recorded in `children[]`
at all.

This plan is the only outstanding item in Phase 01. The other 34 UAT tests pass; plans 01-01
through 01-04 are executed, code-reviewed, and verified. **No new `D-NN` decision from
`01-CONTEXT.md` is implemented here** — this is remediation of a defect in the developer tooling
built by Plan 01-01. D-02 (loopback-only binding, never log secrets) and D-03 (five-minute idle
timeout) are untouched by this plan and must remain exactly as they are.

**Requirement linkage:** `SEC-01` because the failed acceptance criterion belongs to Plan 01-01
(`requirements: [SEC-01, SEC-05]`). `SEC-04` because an orphaned server process is a live
counterexample to it: the auto-lock requirement promises the in-memory session key is destroyed,
and a surviving node.exe the user believes they stopped keeps an unlocked vault session — with its
Vault Key buffer — resident and its port bound after the user has walked away from the terminal.

<objective>
Make a single Ctrl-C in a real Windows PowerShell terminal kill the entire `npm run dev` process
tree with no confirmation question and no survivor, and make that outcome provable by a command
rather than only by a human watching Task Manager.

Three changes, in dependency order:

1. **Remove every Windows script shim from dev.mjs's own subtree.** Resolve the real JavaScript
   entrypoints of the TypeScript compiler and Vite and run them under `node` directly, instead of
   going through the npm wrapper. This removes the only processes in the subtree that are capable
   of asking the batch-job question at all.
2. **Give each child its own Windows process group.** With the group isolation in place the console
   broadcast never reaches the children, so the tree is still intact and walkable when dev.mjs's
   own tree-kill runs — and that tree-kill is now awaited to completion before dev.mjs exits.
3. **Prove it without a human.** A harness spawns dev.mjs, waits for the stack to be up, captures
   the complete descendant PID set, asserts none of them is a command interpreter or script shim,
   triggers a shutdown, and asserts every captured PID is gone and both ports are free.

Purpose: closing the last open UAT gap in Phase 01, and removing a class of failure where a process
holding an unlocked vault session survives what the developer believes was a full stop.

Output: a rebuilt spawn/shutdown layer, a repeatable shutdown verification command, unit coverage
of the spawn specs, and the documented run instructions the repository currently lacks.
</objective>

    process tree? It must leave the machine exactly as it found it, whether it passes or fails.

    Sequence:

    1. **Guard the ports.** Import `DEV_PORTS` from `./dev-spec.mjs`. For each port, attempt to

       slow on a cold `server/dist`. On timeout, print the transcript and fail.

       `-NoProfile` and a `Get-CimInstance Win32_Process` query projected to `ProcessId`,

       row matches). Do not use `wmic` — it is removed from current Windows builds. On other
       platforms, use `ps -eo pid=,ppid=,args=` and parse it.

       when an assertion fails:
       - The descendant set is non-empty and contains at least four processes — the three children
         plus at least the compiled-server watcher's inner worker. Fewer than that means the
         snapshot is wrong, and every later assertion would pass vacuously.
       - No descendant is the Windows command interpreter, matched case-insensitively on the
         process name.

         on the batch and command file extensions at a path boundary.

       question the user hit can no longer originate inside dev.mjs's subtree.

       end that stream.

       fresh process enumeration **and** both ports bind free again. Report any survivor with its
       recorded name and command line — a survivor's own command line may no longer be readable
       once it is being torn down, which is exactly why it is captured up front in step 4.

       confirmation question. This catches the reported symptom directly rather than by proxy: with
       the subject's output redirected to a pipe, that question lands in the transcript instead of
       on a console, and the process that asked it would then block forever waiting for an answer
       that never comes — which step 7's timeout also catches.
    9. **Report and clean up.** Print a short pass/fail table of each assertion. In a `finally`

<threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Terminal console → dev-stack process tree | Windows broadcasts console control events across this boundary to every attached process at once, uncoordinated with any userland handler. This is the boundary the whole gap lives on. |
| dev.mjs → spawned child commands | Argument vectors cross here into process creation. |
| Verification harness → machine-wide process table | The harness reads every process's command line on the machine, including processes belonging to unrelated software. |
| Stopped dev stack → still-resident vault session | A process the developer believes is stopped may still hold an unlocked Vault Key buffer in memory and a bound loopback port. |

## STRIDE Threat Register

ASVS Level 1. Blocking threshold: `high`. **No package-manager install task exists in this plan** —
it adds no dependency and changes no manifest entry other than one npm script — so the package
legitimacy gate does not apply and `T-01-SC` from Plan 01-01 is unchanged and still in force.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-12 | Information Disclosure | Orphaned `server/dist/src/app.js` process surviving a stop | high | mitigate | This is the security face of `G-01-31`: a surviving server process keeps an unlocked vault session, its Vault Key buffer, and its loopback port alive after the developer believes the stack is stopped, defeating the SEC-04 promise that locking destroys the in-memory key. Task 1 makes the tree-kill await completion and reach the watcher's inner worker; Task 2 asserts zero survivors and both ports released; Task 3 confirms it under a real console interrupt. |
| T-01-13 | Elevation of Privilege | `spawn`/`spawnSync` with the shell option enabled in `scripts/dev.mjs` | medium | mitigate | Every spawn in the rewritten script sets the shell option to `false`, so arguments are passed as a vector and never concatenated into a command string. The current code relies on all arguments being hardcoded constants; removing the shell removes the reliance. The unit test in Task 1 asserts the option on every spec, so it cannot regress silently. Also clears the `DEP0190` deprecation warning this runtime now emits. |
| T-01-14 | Information Disclosure | `scripts/verify-dev-shutdown.mjs` machine-wide process enumeration | medium | mitigate | Command lines of unrelated processes routinely carry credentials and tokens. The harness prints and retains command lines only for processes inside the subject's own descendant tree; everything else exists solely as parent-child index entries, is never printed, and the harness writes no report file at all. |
| T-01-15 | Denial of Service | Detached children surviving a force-kill of dev.mjs | medium | accept | Console-detaching the children is exactly what makes them immune to the broadcast, and the same property means a `taskkill /F` aimed at dev.mjs alone leaves them running. Accepted: force-killing the supervisor is a deliberate act, the developer-facing recovery is documented by the harness's own cleanup path, and the alternative — leaving children on the shared console — is the defect being fixed. |
| T-01-16 | Tampering | Bypassing the workspace `dev` script for the client | low | accept | The client spec now invokes Vite's entrypoint directly rather than through `client/package.json`'s `dev` script, so a future change to that script would not take effect. Accepted with a drift guard rather than a mechanism: the Task 1 unit test asserts the script is still exactly `vite`, and fails loudly the moment someone changes it. |
| T-01-17 | Denial of Service | Harness run colliding with a developer's own running stack | low | mitigate | The harness refuses to start if either port is already bound, and reports which one, rather than fighting for the port or killing a process it does not own. |
