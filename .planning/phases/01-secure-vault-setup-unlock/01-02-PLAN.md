    and this is the last moment it is free to change.

    Undo cost after the next task ships: every existing vault must be decrypted with the old scheme

    (`version: 1`) and records its own cipher name, so a future migration is *possible*; it is the
    data movement, not the code, that makes this expensive.

    Research assumptions A1 (sidecar layout), A2 (auth-tag-as-oracle), and A4 (cipher choice) are

  <options>
    <option id="as-planned">
      <name>As planned — sqlcipher cipher mode, JSON sidecar, auth-tag oracle</name>
      <pros>
        AES-256-CBC + HMAC matches the "AES-256" security bar stated in the roadmap success
        criteria. The sidecar is plain JSON, so it is inspectable and debuggable, and it is the only
        place the wrapped Vault Key can live (the key cannot be stored inside the file it unlocks).
        One Argon2id call per unlock keeps the ~0.5-1s latency target. The cipher name is recorded
        in the sidecar, so a future re-key knows what it is migrating from.
      </pros>
      <cons>
        Two files must stay together; losing the sidecar loses the vault permanently, since D-05
        provides no recovery path. AES-CBC+HMAC is encrypt-then-MAC rather than a single-pass AEAD.
      </cons>
    </option>
    <option id="chacha20">
      <name>Same layout, but the library-default chacha20 cipher mode</name>
      <pros>
        ChaCha20-Poly1305 is a modern single-pass AEAD and is this library's default, so it is the
        best-tested path through the extension. Arguably a stronger choice than sqlcipher mode.
        Would also open the door to the library's partial-plaintext-header feature later.
      </pros>
      <cons>
        The roadmap success criteria and PROJECT.md describe the vault as AES-256, so the shipped
        artifact would not match its own written security description without amending those
        documents.
      </cons>
    </option>
    <option id="separate-verifier">
      <name>As planned, but add a separate Argon2id password-verifier hash</name>
      <pros>

    **`crypto.ts`** — implement `deriveMasterKey(password: string, salt: Buffer): Promise<Buffer>`
    calling `argon2.hash` with `config.KDF_PARAMS`, the supplied salt, and `raw: true`, returning a
    32-byte Buffer. Implement `wrapKey(plaintext: Buffer, key: Buffer): WrappedBlob` using
    `createCipheriv("aes-256-gcm", key, iv)` with a freshly generated 12-byte `randomBytes` IV on
    every single call, returning base64 ciphertext, IV, and the 16-byte tag from `getAuthTag()`.
    Implement `unwrapKey(blob: WrappedBlob, key: Buffer): Buffer` using `createDecipheriv`, calling
    `setAuthTag` before `final()`. Export `generateVaultKey()` returning `randomBytes(32)`.

    Because the derivation runs in raw mode, node-argon2's PHC-string comparison helper cannot work
    against these outputs — do not add a separate password-verifier field and do not make a second
    derivation call. The authentication-tag mismatch thrown by `final()` IS the password-correctness
    oracle; let it propagate and let the caller translate it through `vaultAuthError()`.

    **`vaultMeta.ts`** — `vaultExists()` returns true when both `config.VAULT_META_PATH` and
    `config.VAULT_DB_PATH` exist. `readVaultMeta(): VaultMeta` parses the sidecar and validates it
    against a zod schema mirroring the `VaultMeta` contract, throwing on a malformed file.
    `writeVaultMetaAtomic(meta: VaultMeta)` serializes, writes to a sibling temp path, fsyncs, then
    renames over the real path — a torn write here destroys the only path back into the vault, and
    D-05 provides no recovery. Create `config.VAULT_DIR` if absent with mode `0o700`.

    **`connection.ts`** — `openVaultDb(path: string, vaultKey: Buffer): Kysely<VaultDbSchema>`. The
    statement order is load-bearing and must not be reordered or interleaved: construct
    `new Database(path)`, then `db.pragma("cipher='sqlcipher'")`, then `db.key(vaultKey)` using the
    Buffer-binding form rather than the passphrase-string PRAGMA form (a 32-byte random key is
    binary, not a passphrase), then a cheap forcing read `db.pragma("user_version")` wrapped in
    try/catch. The keying call itself does not throw on a wrong key — without the forcing read a
    wrong key surfaces much later as unexplained corruption. Convert any failure of that forcing
    read into `vaultAuthError()`. Return
    `new Kysely<VaultDbSchema>({ dialect: new SqliteDialect({ database: db }) })` — Kysely's
    `SqliteDialectConfig` is a structural interface with no package-name check, so the
    `better-sqlite3-multiple-ciphers` instance is passed directly with no `package.json` alias.

    Also export `initSchema(db)` creating the `schema_version` table if absent and inserting
    `{ version: 1, applied_at: <ISO now> }`. This is a plain Kysely DDL call executed once at vault
    creation. This stack has no ORM push or migrate command, so no separate schema-push step exists
    or should be added.

    **`session.ts`** — fill the Plan 01-01 stub with the module-scoped singleton from RESEARCH.md
    Pattern 5. Private `vaultKey: Buffer | null`, `db: Kysely | null`, `idleTimer`.
    `unlockSession(key, db)` stores both and arms the timer. `armIdleTimer()` clears any existing
    timer and sets a new one for `config.IDLE_TIMEOUT_MS` firing `lock`. `lock()` performs all four
    steps inside one synchronous function body with no early return: zero the key buffer in place
    with `fill(0)`, null the reference, destroy the Kysely instance so the underlying connection
    closes, and clear the timer. Splitting these across separate call sites is exactly the
    half-implemented-lock failure mode PITFALLS.md documents. `isUnlocked()` returns a boolean;
    `getVaultKey()` and `getDb()` throw rather than returning null when locked, so no caller can
    operate on a dead handle by accident.

    **`routes.ts`** — an Express router mounted at `/api/vault` by `app.ts`, replacing the Plan
    01-01 placeholder. Two routes in this plan; Plans 01-03 and 01-04 add the rest.

    `GET /status` returns a `VaultStatus` built from `vaultExists()`, `session.isUnlocked()`, the
    sidecar's `totp.enabled` when the vault exists (false otherwise), and `config.IDLE_TIMEOUT_MS`.
    It reads no secret and requires no unlocked session, and it must not sit behind
    `requireUnlocked` — the client polls it, and polling must never keep a session alive.

    `POST /init` is validated by a zod schema of
    `{ masterPassword: string, noRecoveryAcknowledged: literal true }`. Behavior in order:
    respond HTTP 409 `{ error: "Vault already exists" }` when `vaultExists()`; reject an empty or
    whitespace-only password with HTTP 400 before any derivation call; score the password with
    `@zxcvbn-ts/core` loaded with the `@zxcvbn-ts/language-common` and `@zxcvbn-ts/language-en`
    dictionaries and respond HTTP 400 with `{ error, score, feedback }` when the score is below
    `config.MIN_PASSWORD_SCORE`. This is the one endpoint in the phase whose failure response is
    deliberately specific rather than generic — at creation time there is no secret to protect and
    the user needs actionable feedback; every other auth-path failure in this phase collapses to
    the single generic 401.

    On success: generate a 16-byte salt, derive the Master Key, generate a 32-byte Vault Key, wrap
    the Vault Key with the Master Key, open `config.VAULT_DB_PATH` with the Vault Key, run
    `initSchema`, read the `schema_version` row back through that same Kysely handle to prove the
    encrypted database round-trips, write the sidecar atomically (`version: 1`, `cipher` set to the
    mode selected in Task 1, `noRecoveryAcknowledged: true`, the KDF params from config, the salt,
    the wrapped Vault Key, and `totp: { enabled: false, wrappedSecret: null, backupCodeHashes: [] }`),
    zero the Master Key buffer, call `session.unlockSession(vaultKey, db)`, and respond HTTP 201
    with a `VaultStatus`. The response body carries no key material of any kind. Wrap the whole
    sequence so a mid-sequence failure removes any partially written database and sidecar rather
    than leaving an unopenable vault behind.

    **`crypto.test.ts`** — a wrap/unwrap round trip recovers the exact plaintext Buffer; unwrapping

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → local API (`127.0.0.1:5174`) | The master password crosses here in plaintext over loopback HTTP. This is the only place a user secret crosses a process boundary. |
| Node process → `.vault/vault.meta.json` | Unencrypted sidecar. Everything written here is readable by any process running as this user. |
| Node process → `.vault/vault.db` | Whole-file-encrypted. Ciphertext at rest; the key exists only in process memory. |
| Node process memory → everything else | The Master Key and Vault Key Buffers live here and must not escape into a response, a file, or a log. |

## STRIDE Threat Register

ASVS Level 1. Blocking threshold: `high`.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | AES-256-GCM IV reuse in `crypto.ts` `wrapKey` | critical | mitigate | A fresh `randomBytes(12)` IV is generated inside `wrapKey` on every call, never passed in, cached, or derived; `crypto.test.ts` asserts two wraps of identical input produce different IVs. IV reuse under GCM can leak the authentication key, which is why this is rated critical rather than high. |
| T-02-02 | Elevation of Privilege | Offline brute force against a stolen sidecar-and-database pair | high | mitigate | Argon2id at the parameters measured in Plan 01-01, with a unique 16-byte CSPRNG salt per vault stored in the sidecar. Memory-hardness is what makes a stolen pair expensive rather than trivial to attack. |
| T-02-03 | Information Disclosure | Key material escaping in the `POST /init` response body | high | mitigate | The handler responds with a `VaultStatus` and nothing else; an acceptance criterion asserts the response contains only those four fields and no base64 blob. The Master Key buffer is zeroed before the response is sent. |
| T-02-04 | Spoofing | A wrong or absent key opening `vault.db` without visible failure | high | mitigate | `openVaultDb` issues a forcing read immediately after keying and converts failure into `vaultAuthError()`. The keying call alone never throws, so without the forcing read the failure surfaces later as data corruption in Phase 2. |
| T-02-05 | Tampering | Torn sidecar write during creation leaves an unopenable vault | high | mitigate | Temp-file write, fsync, atomic rename in `writeVaultMetaAtomic`; the init handler removes partial artifacts on any mid-sequence failure. D-05 provides no recovery path, so a torn sidecar is permanent data loss. |
| T-02-06 | Information Disclosure | Master password captured by a browser password manager or persisted client-side | medium | mitigate | `autoComplete="new-password"` on both inputs and `autoComplete="off"` on the form; the value lives in component state only; a repo-wide grep bans Web Storage APIs in `client/src`. Mitigated rather than accepted at L1 because it sits on a primary trust boundary. |
| T-02-07 | Information Disclosure | Sidecar readable by other users on a shared machine | medium | mitigate | `VAULT_DIR` is created with mode `0o700`. | T-02-08 | Denial of Service | Repeated `POST /init` exhausting memory through Argon2id | low | accept | Reachable only from loopback by a process already running as this user, which by then can read the vault files directly. | T-02-09 | Repudiation | No record of when the vault was created or by what | low | accept | `createdAt` is written into the sidecar, which covers the only event this plan produces. A full access audit log is TRUST-03, delivered in Phase 3. |
