<objective>
Expand the tracer outward along the unlock axis: a returning user unlocks the vault they created,
a wrong password is rejected without revealing why, and the vault locks itself for real after five
minutes of inactivity.

This plan adds no new architectural layer. It reuses `crypto.ts`, `connection.ts`, and the session
singleton from Plan 01-02 exactly as they are, and adds two routes, one client screen, and the
lifecycle wiring.

Purpose: the lock model is the single most commonly half-implemented part of a vault. A "lock" that
changes a UI route while the key stays live in memory passes every visual check and fails the
requirement completely. This plan makes the lock mechanically provable — the key buffer is zeroed,
the database handle is closed, and a direct HTTP call after the lock is denied.

Output: a vault that can be unlocked, that rejects wrong passwords indistinguishably, and that
locks itself on schedule whether or not the browser cooperates.
</objective>

<assumption_delta_decision>

## Assumption-Delta: required → optional (TOTP second factor)

The assumption-delta scan fired on this phase with a single `optional` signal, from the roadmap
success criterion *"User can enable **optional** TOTP-based 2FA, and once enabled must supply both
the master password and a valid TOTP code to unlock."* The transition is required → optional: a
vault has either one factor or two, decided per vault at runtime.

**Decision: add alongside, do not promote.** TOTP is not promoted to an always-required field and
the single-factor path is not treated as a degenerate case of the two-factor path. Instead the
unlock contract is designed from the start to carry both shapes as first-class branches:

- `POST /api/vault/unlock` accepts `{ masterPassword: string, totpCode?: string }` from this plan
  onward. The optional field is defined in the zod schema **now**, in Plan 01-03, even though
  nothing populates it until Plan 01-04. Adding it later would change a shipped request contract.
- `GET /api/vault/status` already carries `totpEnabled`, so the client knows which shape to render
  before it submits anything, without a probing round trip.
- The unlock handler branches on the sidecar's `totp.enabled`, not on whether `totpCode` was
  supplied. A code supplied to a vault without 2FA is ignored, not an error — an error there would
  leak the vault's 2FA state to an unauthenticated caller.

**Consequence for Plan 01-04:** enabling 2FA changes only which branch the handler takes and one
field in the sidecar. It adds no endpoint, no request-shape migration, and no change to this
plan's client code beyond rendering one additional input.

This checkpoint is advisory and does not block the phase.

</assumption_delta_decision>

    Add the unlock and lock routes to the existing `/api/vault` router. Reuse the crypto, session,
    and connection modules exactly as Plan 01-02 built them — this task creates no new crypto and no

    **`POST /unlock`** is validated by a zod schema of
    `{ masterPassword: string, totpCode: string optional }`. The optional second-factor field is
    defined now even though nothing populates it until Plan 01-04; see this plan's
    `<assumption_delta_decision>` block for why. Behavior:

    Respond HTTP 409 `{ error: "Vault does not exist" }` when `vaultExists()` is false — this is a
    state fact the client already learns from `GET /status`, not a secret. If the session is already
    unlocked, arm the idle timer and return the current `VaultStatus` without re-deriving.

    Otherwise: read the sidecar, derive the Master Key from the submitted password and the stored
    salt using the stored KDF parameters (read them from the sidecar, not from config — a vault
    created with different parameters must still open), then call `unwrapKey` on the stored
    `wrappedVaultKey`. Open the database with the recovered Vault Key. If the sidecar's
    `totp.enabled` is true, verify the second factor as well — Plan 01-04 supplies that
    implementation; in this plan, when `totp.enabled` is true and no verifier exists yet, fail
    closed through `vaultAuthError()` rather than unlocking. On success call
    `session.unlockSession(vaultKey, db)`, zero the Master Key buffer, and respond HTTP 200 with a
    `VaultStatus`.

    Every failure on this route — an authentication-tag mismatch from `unwrapKey`, a failed forcing
    read from `openVaultDb`, an unreadable or malformed sidecar, and later a bad second factor —
    must be caught and converted into `vaultAuthError()`, producing the byte-identical HTTP 401
    `{ error: "Unable to unlock" }`. Nothing in the response body, the status code, the header set,
    or the response timing may differ by cause. Do not add a field describing which check failed,
    do not vary the message, and do not return early on one branch in a way that measurably
    shortens the response. To keep timing from becoming the distinguisher, the handler performs the
    key derivation before checking anything that could short-circuit it.

    **`POST /lock`** calls `session.lock()` unconditionally and responds HTTP 204. It is safe to
    call when already locked and safe to call repeatedly, because the client fires it from page
    lifecycle events that may or may not have a live session behind them.

    **`server/src/middleware/rateLimit.ts`** exports `unlockRateLimit`, an `express-rate-limit`
    instance scoped to the unlock route: a small window with a low request ceiling, an in-memory
    store, and a response that reuses the same generic failure body rather than announcing that a
    limit was hit. Mount it on `POST /unlock` only — never on `/status` or `/lock`, both of which
    the client calls automatically. If the developer rejected `express-rate-limit` at Plan 01-01
    Task 1, implement the same behavior as a small in-memory counter in this file instead and note
    the substitution in the SUMMARY.

    **`requireUnlocked.ts`** now has a real session to gate against. Confirm it arms the idle timer
    on pass, and confirm the route mounting in `app.ts`: `requireUnlocked` guards vault data routes
    only. `GET /status`, `POST /init`, `POST /unlock`, and `POST /lock` must all sit outside it.
    `GET /status` in particular is polled by the client, and putting it behind the timer-arming
    middleware would silently defeat the five-minute auto-lock entirely — that is this plan's
    second listed prohibition. There are no vault data routes yet (Phase 2 adds them), so in this
    plan `requireUnlocked` is mounted on nothing and its correctness is asserted by test rather
    than by use.

    **`unlock.test.ts`** — with `VAULT_DIR` pointed at a fresh temp directory per test, create a
    vault, then assert: the correct password returns 200 and a status showing unlocked; a wrong
    password returns 401 and the vault remains locked; unlocking after a wrong attempt still

    exposing key material, whether a key buffer is currently held and whether that buffer's bytes

    **`autolock.test.ts`** — use vitest's fake timers so a five-minute wait is instantaneous, with
    `VAULT_DIR` pointed at a fresh temp directory per test. Assert:

    1. After a successful unlock, `isUnlocked()` is true and a key buffer is held.
    2. Advancing time by just under `IDLE_TIMEOUT_MS` leaves the vault unlocked.
    3. Advancing past `IDLE_TIMEOUT_MS` locks it: `isUnlocked()` becomes false, the retained buffer
       reports as all zero bytes, and `getVaultKey()` and `getDb()` both throw.
    4. After that automatic lock, an HTTP request to a route behind `requireUnlocked` returns 401 —
       tested over the HTTP surface, not by calling the session module directly, because the
       requirement is that decrypted data is unreachable through any code path. Mount a temporary
       test-only route behind `requireUnlocked` inside the test file if no vault data route exists
       yet.
    5. A request through `requireUnlocked` while unlocked re-arms the timer: after such a request,
       advancing by just under `IDLE_TIMEOUT_MS` from the *request* leaves the vault unlocked, even
       though more than `IDLE_TIMEOUT_MS` has now elapsed since the original unlock.
    6. Repeatedly calling `GET /api/vault/status` does NOT re-arm the timer: with a status call
       every minute of fake time, the vault still locks at the five-minute mark measured from the
       unlock. This is the direct test of this plan's second prohibition, and it is the assertion
       that catches the most likely silent failure — an auto-lock that never fires because the UI
       polls.
    7. `POST /api/vault/lock` locks immediately and is safe to call again while already locked.
    8. Unlocking again after an automatic lock succeeds, so locking leaves no corrupt state behind.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → local API (`127.0.0.1:5174`) | The master password crosses here in plaintext over loopback HTTP on every unlock attempt. |
| Unauthenticated caller → `POST /api/vault/unlock` | The only endpoint an attacker can meaningfully attack; every response it emits is an information channel. |
| Node process memory → post-lock state | After a lock, no code path may reach the Vault Key or the open database handle. |
| Browser page lifecycle → server lock state | The client can request a lock but must never be the thing that guarantees one. |

## STRIDE Threat Register

ASVS Level 1. Blocking threshold: `high`.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Information Disclosure | `POST /unlock` response distinguishing failure causes | high | mitigate | Every failure converts to `vaultAuthError()` producing one byte-identical 401; the key derivation runs before any short-circuiting check so response timing does not become the distinguisher; `unlock.test.ts` asserts the wrong-password and corrupted-ciphertext responses are identical; a grep bans any response field naming a specific failure. |
| T-03-02 | Information Disclosure | Two-step unlock revealing that a password was correct | high | mitigate | The second-factor field renders alongside the password from the start based on the non-secret `totpEnabled` status flag, and both submit in one request. | T-03-03 | Elevation of Privilege | Key surviving in memory after a lock | critical | mitigate | `lock()` zeroes the buffer in place, drops the reference, destroys the database handle, and clears the timer in one function body; `autolock.test.ts` asserts the retained buffer reads as all zeros and that both accessors throw afterwards. Rated critical because a lock that does not destroy the key means the vault is never actually locked. |
| T-03-04 | Elevation of Privilege | Auto-lock silently never firing because the client polls status | high | mitigate | `GET /status` is deliberately mounted outside `requireUnlocked`, the only place the timer is armed; `autolock.test.ts` assertion 6 polls status every simulated minute and requires the vault to lock on schedule anyway. | T-03-05 | Spoofing | Offline brute force against the unlock endpoint by a local process | high | mitigate | Argon2id's memory-hardness makes each attempt expensive; `unlockRateLimit` adds an in-memory backoff on the unlock route only. Deliberately no permanent lockout: D-05 provides no recovery, so a lockout would destroy the vault as effectively as an attacker would. |
| T-03-06 | Information Disclosure | Master password captured by a password manager or persisted client-side | medium | mitigate | `autoComplete="current-password"` on the input, `autoComplete="off"` on the form, state cleared on both success and failure, and a repo-wide grep banning Web Storage APIs. On a primary trust boundary, so mitigated at L1. |
| T-03-07 | Tampering | Client lock signal trusted as the enforcement point | high | mitigate | The server timer runs independently of any client signal; `session-signals.ts` carries a header comment stating it is an accelerant only; `autolock.test.ts` exercises the lock with no client involvement at all. |
| T-03-08 | Denial of Service | Rate limiter locking out the legitimate user | medium | accept | Accepted with rationale: the limit is a short in-memory window, not a persistent lockout, and it resets on process restart. The alternative — a durable lockout — is strictly worse here, because with no recovery path a lockout is indistinguishable from data loss. |
| T-03-09 | Repudiation | No record of failed unlock attempts | low | accept | A failed-attempt log is part of TRUST-03's audit trail in Phase 3. Accepting here means Phase 1 does not record attempts; it does not weaken the unlock control itself. |
